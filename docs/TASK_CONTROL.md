# 基本タスク制御を理解する

この段階のゴールは、**仕事を起動し、優先度に従って切り替え、中断した仕事を続きから再開し、終了した仕事には戻らないこと**です。OSEK OS 2.2.3 の Basic Task を土台に、Lean のモデル、一般の設定についての証明、独立したテスト、QEMU 上の実行を組み合わせます。

最初の固定 3 タスクの教材は [入門ガイド](GETTING_STARTED.ja.md) に残しています。ここではタスク数、優先度、起動要求の上限を変えられるモデルを説明します。全体の配置は [README](../README.md) を参照してください。

## 1. タスクと起動要求は違う

タスクは、実行したい仕事の定義です。起動要求は「その仕事を 1 回行ってほしい」という依頼です。同じタスクに 2 回依頼が届いた場合、2 回目の仕事は 1 回目が終わるまで待ちます。

設定はタスクごとの次の 3 項目です。タスク ID はリストの位置、つまり `0, 1, 2, ...` です。

| 項目 | 意味 | 例 |
|---|---|---|
| `priority` | 数値が大きいほど先に実行する | `1` より `3` が優先 |
| `maxActivations` | 現在実行中・中断中の分を含む、未完了の依頼数の上限 | `2` なら実行中にもう 1 回依頼できる |
| `preemptive` | より高い優先度の仕事が来たときに中断できるか | `false` なら `Schedule` または終了まで継続 |

設定には 1 個以上のタスクが必要で、各起動上限は 1 以上です。モデルは任意個数の静的設定を扱います。優先度 `0` も使えます。有限時間・有限メモリで扱える具体的な大きさは実行環境に依存します。

外から見えるタスクの状態は次の 3 つです。

| 状態 | 意味 |
|---|---|
| `SUSPENDED` | 未完了の起動要求がない |
| `READY` | 起動済みで実行順を待っている |
| `RUNNING` | 現在選ばれているタスク。単一コアなので高々 1 個 |

`GetTaskState` はタスク全体の状態を返します。同じタスクに待ち要求があっても、現在そのタスクを実行していれば `RUNNING` です。

## 2. 同じ優先度なら、依頼が来た順番

同じ優先度のタスク A と B に `A → B → A` の順に依頼が届くと、実行順も `A → B → A` です。A の依頼数を数えるだけでは、この順序を表現できません。そのため、モデルには **起動要求ごとの待ち行列**があります。

一方、実行中の A が高優先度の C に中断された場合、A の続きは新しい依頼より先に再開します。

| 操作 | 実行中 | 待っている仕事 | 理由 |
|---|---|---|---|
| A を起動 | A | なし | 実行できる仕事が A だけ |
| B を起動 | A | B | 同じ優先度では中断しない |
| A をもう一度起動 | A | B、次の A | 新しい依頼は末尾へ |
| 高優先度の C を起動 | C | A の続き、B、次の A | 実行中の A の位置を保存 |
| C が終了 | A の続き | B、次の A | 中断された A を再開 |
| A が終了 | B | 次の A | 依頼順に進める |

`Schedule` は同じ優先度への順番交代ではありません。自分より **高い** 優先度の仕事が待っているときに切り替える操作です。時間切れで順番に切り替えるラウンドロビン方式はありません。

## 3. 基本の 6 操作

以下のエラー名は仕様の意味を説明するための表記です。テスト用プロトコルの数値はプロジェクト独自であり、OSEK の C ヘッダーやポインター ABI とは別です。

| 操作 | 成功したとき | 主なエラー |
|---|---|---|
| `ActivateTask(id)` | 依頼を 1 個追加。許可された場面なら高優先度タスクに切り替える | ID が不正なら `E_OS_ID`、上限なら `E_OS_LIMIT` |
| `TerminateTask()` | 現在の依頼を完了し、次の仕事へ移る。成功した呼び出し元には戻らない | タスク外なら `E_OS_CALLEVEL`、資源を保持していれば `E_OS_RESOURCE` |
| `ChainTask(id)` | 現在の依頼を完了すると同時に、指定タスクへ新しい依頼を追加。成功時は戻らない | `E_OS_ID`、`E_OS_LIMIT`、`E_OS_CALLEVEL`、`E_OS_RESOURCE` |
| `Schedule()` | 高優先度の仕事に実行を譲り、自分が再び選ばれたら続きへ戻る | `E_OS_CALLEVEL`、`E_OS_RESOURCE` |
| `GetTaskID()` | 現在のタスク ID。タスクがなければ無効 ID | 対応する呼び出し場所では成功 |
| `GetTaskState(id)` | 指定タスクの状態 | ID が不正なら `E_OS_ID` |

`ChainTask` の失敗時には、呼び出したタスクは終了しません。先に終了してから起動を試す実装では、起動に失敗したときに仕事を失ってしまいます。対象の検査を済ませてから、一つの状態遷移として実行します。

`ChainTask(自分)` は現在の依頼を新しい依頼に置き換えるので、起動要求数が上限に達していても成功します。新しい実行は先頭から始まります。同じ優先度ですでに待っている依頼は先に実行されます。

複数の不正条件が同時にある場合、このプロジェクトは「呼び出し場所 → 資源保持 → ID → 起動上限」の順で検査します。この順序を OSEK 全体で義務づけられたエラー優先順位としては扱いません。エラー時には状態全体を保存します。

## 4. 中断と終了を区別する

中断されたタスクには「再開する場所」が必要です。Lean の一般モデルでは、説明とテストのための `pc` という進行カウンターを使います。`pc = 1` まで進んだ A が中断されたら、再開後も `pc = 1` です。

終了したタスクの古い続きには戻りません。次の起動要求の `pc` は `0` です。結果の `discard` は「呼び出し元の古い続きは捨てる」という指定で、`TerminateTask` と `ChainTask` が成功したときだけ真になります。通常の優先度による中断とは区別します。

`pc` は実 CPU の命令アドレスではありません。QEMU 側ではタスクごとのスタックと保存したレジスターを使い、本当に関数の途中へ戻れることを別に検査します。一般モデルと小さい機械向けアダプターとの対応は差分テストで確認しており、機械語までの形式的な精密化証明ではありません。

## 5. 割り込み・資源との境界

一般モデルにはカテゴリ 2 ISR の入場・退場と入れ子の深さがあります。ISR 内の `ActivateTask` は起動要求を記録しますが、その場ではタスクを切り替えません。一番外側の ISR を抜けるときに切り替えを判断します。ISR が中断したタスクは `current` に保持され、ISR 内の `GetTaskID` からも参照できます。

| 呼び出し場所 | `ActivateTask` | 終了・連鎖・`Schedule` | 2 つの問い合わせ |
|---|---|---|---|
| 実行中タスク | 対応 | 対応 | 対応 |
| ISR2 | 対応。切り替えは最外側の退場時 | 呼び出し場所エラー | 対応 |
| タスクがない初期状態 | プロジェクトの呼び出し場所エラー | 呼び出し場所エラー | 無効 ID／`SUSPENDED` を返せる |
| フック、ISR1、その他 | 今回は対象外 | 今回は対象外 | 今回は対象外 |

OSEK が認める一部フックからの問い合わせも、今回の呼び出し場所モデルにはまだ含めません。最初の起動にはテスト用の ISR 入場・起動・退場を使います。これは `StartOS` や OIL の autostart の実装ではありません。

資源保持中の `TerminateTask`、`ChainTask`、`Schedule` を拒否するために、モデルの呼び出し情報に「資源を保持している」という印を渡せます。この印は **外側のシステムからの前提条件**です。資源の所有者管理、優先度上限プロトコル、`GetResource` / `ReleaseResource` は実装していません。資源を使う実 OS に組み込む場合には、これらを実装して印が真実になることも保証する必要があります。

OSEK の割り込み禁止 API の区間から OS サービスを呼ぶことには制約があります。今回のモデルには `DisableAllInterrupts` / `SuspendAllInterrupts` / `SuspendOSInterrupts` の状態管理がありません。この制約を呼び出し側が守ることを前提とし、ISR の入れ子深さだけで代用しません。`E_OS_DISABLEDINT` を OSEK 2.2.3 の標準エラーとして追加してもいません。

## 6. 一般モデルと QEMU 用アダプター

| 層 | 対応する設定 | 役割 |
|---|---|---|
| `Task/Model.lean` | 任意個数の静的タスク、自然数の優先度・正の起動上限 | 仕様としての状態遷移と証明 |
| `Task/Protocol.lean` / `TaskMain.lean` | 同じ設定 | 人が読めるテスト入出力 |
| `Task/Scalar.lean` | 最大 4 タスク、優先度 0〜15、起動上限の合計 8 以下、ISR 深さ 15 以下 | 固定幅の値として表し、Lean から C を生成 |
| QEMU の移植層 | 具体的なテスト設定 | スタック、レジスター、実際の制御移動 |

小さいアダプターを設ける理由は、一般モデルのリストや自然数のランタイムを、そのまま最小の機械環境に持ち込まずに状態遷移を動かすためです。アダプターも Lean のソースから C へ生成しますが、一般モデルとは別の表現なので、独立した Python の計算結果と照合します。

## 7. 検証をどう読むか

主な検証は次のように役割が分かれます。

| 検証 | 確かめること | それだけでは確かめられないこと |
|---|---|---|
| Lean の証明 | 各定理の前提を満たす設定・状態について、結論が成り立つ | C コンパイラーやアセンブリー、ハードウェアの正しさ |
| 独立 Python オラクルとの比較 | 具体的な入力で、別々に書いたスケジューラーの判断が一致する | 無限個の入力すべて |
| 有限長の全列挙 | 選んだ設定・操作集合・長さの範囲を漏れなく試す | より長いすべての操作列 |
| QEMU での実行 | 保存したスタック・レジスターで中断から戻り、終了後には戻らない | 実機のタイミング、WCET、全割り込み状況 |

Python オラクルは待ち行列をそのまま移植せず、依頼ごとの順番番号を付け、優先度と順番番号で次の仕事を決めます。短い操作列の全列挙に加え、同順位の `A → B → A`、自己連鎖、失敗時の原子性、中断後の続き、非プリエンプティブ設定、ISR の入れ子、64 タスクの設定を検査します。

```sh
lake build
python3 tests/test_task_control.py build/task-tests
```

生成 C のアダプターもビルドした後には、同じケースを追加で比較できます。

```sh
python3 tests/test_task_control.py build/task-tests --scalar-runner build/task-scalar-host
```

結果は出力先の `task-control.json` に保存します。`T-TASK-CONTROL` が一般モデル、`scalar` 内の `T-TASK-SCALAR` が機械向け表現の比較です。`scalar: null` は後者を実行していないという意味です。

この段階の完了判定では、6 操作の正常系・異常系、一般設定の不変条件、独立オラクルと生成 C の比較、QEMU の実タスク切り替え、説明資料と CI からの再現を組み合わせます。各検証の実行結果は検証レポートで確認してください。
