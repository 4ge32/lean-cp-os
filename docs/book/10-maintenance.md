# 10. プロジェクトを育てる

この章では、後から変更する人が同じ判断を再現できるように、保守の流れを整えます。
小さな変更を通せるようになったら、コードと根拠と教材を一緒に育てましょう。
到達目標は、影響調査からレビューまでの確認を一人で進められることです。

## まず、変更の入口を選ぶ

優先度の例を変える、エラーの意味を変える、CPU 移植を変える、という作業では確認先が違います。
最初に「どんな入力で、観測できる結果がどう変わるか」を一文で書きます。

| 変更 | 最初に読む場所 | 広げる確認 |
|---|---|---|
| 学習用の設定・説明 | `examples/book/`、`docs/book/` | 教材実行、掲載コード、リンク、Book 表示 |
| 状態遷移・サービス契約 | `Task/Model.lean`、`Task/Semantics.lean` | 要求、証明、独立オラクル、容量制限付き実装 |
| タスク数や機械表現の容量 | `Task/Scalar.lean`、`c/task_scalar_host.c` | ビット表現、不正入力、上限値、ターゲット設定 |
| レジスタやスタック切り替え | `target/aarch64/` | ABI、保存対象、QEMU の観測、生成コードとの境界 |
| 検証・公開 | `scripts/`、`.github/workflows/` | 失敗の保存、コミット識別、既存の履歴 URL |

`build/`、`.lake/`、`evidence/` は生成物です。
修正する入口は生成元のソースや設定に置き、生成し直して確認します。

## 影響調査を試す

コミット済みの変更について、比較元を指定して影響候補を出します。
次の例は、一つ前のコミットと現在の `HEAD` の差分です。

```sh
python3 scripts/impact.py HEAD~1
```

出力には `changed_files`、`requirements`、`theorems`、`tests` が並び、
`conservative: true` と表示されます。
実装はファイルとモジュールの対応を使うので、意味上の最小範囲を計算しているわけではありません。
検証スクリプト、ワークフロー、要求表、ツールチェーンの変更は広い影響として扱います。

このスクリプトは **比較元から `HEAD` まで**を見ます。
未コミットの変更は出力に含まれません。
編集中は `git diff` と `git diff --cached` も読み、教材や未追跡ファイルは `git status` で確認します。
Book の説明だけが変わった場合、要求の候補が空でも、教材とリンクの検査は必要です。
完成判定の全検証は、影響候補で間引きません。

## Book をコードと一緒に確認する

Lean と Lake が PATH にある状態で、リポジトリのルートから実行します。
mdBook は準備スクリプトで指定版を配置します。

```sh
bash scripts/bootstrap_mdbook.sh .toolchain/mdbook
lake build
python3 scripts/check_book.py
.toolchain/mdbook/mdbook build
python3 scripts/check_book.py --html build/book --skip-examples
```

最初の Book 検査は、ローカル参照と教材の Lean 実行を確認します。
最後の検査は、生成した HTML のリンクを確認します。
表示も確認する場合は次を実行し、表示されるローカル URL を開きます。
終了は `Ctrl+C` です。

```sh
.toolchain/mdbook/mdbook serve --hostname 127.0.0.1
```

左の章目次、検索、前後の章への移動を試します。
変更した章では、コードが欠けていないか、表が読めるか、演習の答えが開くかも確認します。
コード例を変更したときは、期待する出力と本文の解説も合わせて更新します。

章の追加は `docs/book/SUMMARY.md`、表示設定は `book.toml` が入口です。
本文は `docs/book/`、実行する教材は `examples/book/` に置きます。
コードは mdBook の include で教材から取り込み、本文に別のコピーを持たせません。
Book の検査は学習例の整合性を確認するもので、OS の全検証の代わりにはなりません。

## レビューに必要な情報をそろえる

変更の説明は、実際の利用場面と結果から書き始めます。
例えば「タスク 1 の未完了要求を 2 回まで受け付ける設定例を追加した。
3 回目は状態を変えずに拒否し、終了後は待ち要求を先頭から実行することを検査した」と書けます。

レビュー前には、次を一度通します。

1. 差分を読み、対象外の生成物や無関係な変更が混ざっていないか確認する。
2. 関係する要求、前提、証明、テスト、説明が同じ動作を述べているか確認する。
3. Book の教材実行、ビルド、生成 HTML の検査を通す。
4. 全検証を行い、`exact_commit` とソースの安定性を含めてレポートを読む。
5. 変更の目的、観測結果、実行した検査、残る制限を PR に記録する。

編集中に `--allow-dirty` で実行した場合は、その条件を明記します。
特定コミットの証拠にするには、コミット後に変更のない状態で全検証を実行します。
`verify.py` は `build/` を再生成するため、Book の最終ビルドは全検証の後に行います。
CI の Book 検査とコミット単位の OS 検証は、対象と結果をそれぞれ確認してください。

## ツールと仕様の版を更新する

Lean の基準は `lean-toolchain` です。
Lean を更新すると、証明の挙動だけでなく、生成 C、ランタイム、コンパイラーの出力も変わり得ます。
準備スクリプトの配布版・ハッシュ、CI の設定、生成コードと QEMU の検査まで一つの変更で見直します。
mdBook も準備スクリプトと CI で版をそろえ、更新後の HTML を確認します。

仕様については、現在の動作基準が **OSEK OS 2.2.3**、将来の照合先が
**AUTOSAR CP OS R25-11** である点を保ちます。
新しい版の存在だけを理由に、既存の要求 ID や証拠を新しい版へ付け替えません。
`trace/sources.json` に入手先、具体的な版、文書のハッシュ、確認できた範囲を記録します。
参照箇所の差分を確認し、必要な要求と実装を更新してから検証します。
詳しい出典と利用条件の記録は [SOURCES.md](https://github.com/4ge32/lean-cp-os/blob/main/docs/SOURCES.md) にあります。

## 設計判断を残す

例えば「最大 4 タスク」という制限を変えるなら、数値だけでなく、
どの表現に収めるための制限か、何をテストし、何が未証明かを書きます。
設計資料には、問題、選んだ方法、その理由、検証した範囲、残る課題を短く残します。
学習者に必要な説明は Book に、機械が読む対応は `trace/` に反映します。

公開時は、Book の入口と検証履歴の入口を一緒に確認します。
履歴の `commits/<SHA>/runs/<run-id>-<attempt>/` は参照先として残します。
失敗した実行も意味のある記録です。新しい成功で過去の結果を書き換えません。

## 確かめる

**演習:** 起動上限の教材だけを編集中です。`impact.py HEAD~1` に教材が出ません。
「影響がないので検査不要」と判断してよいでしょうか。

<details>
<summary>答え</summary>

判断できません。`impact.py` は未コミットの差分を見ず、教材と要求の対応も網羅しません。
`git status` と差分を読み、Book の教材検査とビルドを行います。
モデルを変更した場合は関連証明や比較テストも確認し、完成判定には全検証を使います。

</details>
