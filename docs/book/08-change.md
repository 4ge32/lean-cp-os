# 8. 一つの変更を最後まで通す

この章では、高優先度タスクに届く起動要求の上限を **1 回から 2 回**に変えます。
モデル本体には既に複数起動の仕組みがあります。
その設定を変える教材を作り、要求、実装、証明、テスト、説明を結び付けます。
読み終わると、変更に必要な確認先を自分で選べるようになります。

## 試す前に、期待する動作を書く

タスク 0 は低優先度の定常処理、タスク 1 は高優先度の要求処理とします。
「要求を 2 回受け付ける」だけでは、何が 2 回なのか曖昧です。
ここでは **現在の実行分と、まだ終了していない待ち要求の合計を 2 以下にする**と定めます。

| 場面 | 変更前 | 変更後 |
|---|---|---|
| タスク 1 の最初の起動 | 成功し、タスク 0 を中断 | 同じ |
| タスク 1 が終わる前の 2 回目 | `limit`、状態を維持 | 成功し、追加の要求を待ち行列へ |
| 終わる前の 3 回目 | `limit` | `limit`、状態を維持 |
| タスク 1 の最初の終了 | タスク 0 を再開 | タスク 1 の次の要求を先頭から実行 |
| タスク 1 の 2 回目の終了 | 該当なし | タスク 0 を中断位置から再開 |

これはプロジェクトの設定変更です。OSEK が全タスクに上限 2 を要求するわけではありません。
根拠となる複数起動の考え方は OSEK OS 2.2.3 §4.3、
起動サービスは §13.2.3.1 です。
要求の既存の対応先は `LCPO-013` と `LCPO-020` です。
[要求表](https://github.com/4ge32/lean-cp-os/blob/main/trace/requirements.json)で、前提と検証の対応を確認できます。

## まず教材を実行する

リポジトリのルートで実行します。
Lean の準備がまだなら[コマンド集](reference/commands.md)を参照してください。

```sh
lake build
lake env lean examples/book/change.lean
```

成功すると、この教材からの出力はありません。終了コードは `0` です。
各 `#guard` が期待した値を検査し、末尾の `example` が既存定理の適用を検査します。

```lean
{{#include ../../examples/book/change.lean}}
```

教材の `seed` は「タスク 0 が既に動き、進行値が 7」という状態を明示的に置きます。
OS の起動手順を実装したものではありません。
`pc` はモデルの進み具合を観測する値で、CPU のプログラムカウンターではありません。
タスク 1 を 1 ステップ進めておくと、続きからの再開と、新しい要求の開始を区別できます。

## 差分を読み、仕組みを理解する

実質的な設定差分は、2 個目の `TaskConfig` の `maxActivations` だけです。
`priority = 3`、`preemptive = true` はそのままです。

`activate` は `activeCount` を調べ、上限未満なら新しい `Frame` を末尾に追加します。
`terminate` が実行中の要求を取り除くと、`dispatch` は最高優先度の待ち要求を選びます。
したがってタスク 0 の続きより、タスク 1 の次の要求が先に動きます。

| 教材中の値 | 実行中 `(task, pc)` | 待ち行列 |
|---|---|---|
| `seed` | `(0, 7)` | 空 |
| `progressed.state` | `(1, 1)` | `(0, 7)` |
| `second.state` | `(1, 1)` | `(0, 7), (1, 0)` |
| `finishFirst.state` | `(1, 0)` | `(0, 7)` |
| `finishSecond.state` | `(0, 7)` | 空 |

待ち行列の先頭が常に最高優先度とは限りません。選択時に `choose` が優先度を比較します。
実装は [Task/Model.lean](https://github.com/4ge32/lean-cp-os/blob/main/LeanCpOs/Task/Model.lean)で追えます。

## 証明とテストを組み合わせる

末尾の `example` は、設定を `revised` に固定しても、起動失敗時の状態不変性が使えることを示します。
対象状態 `s` は任意です。具体的な `third` 一件を調べる `#guard` より広い主張です。
一方、この定理だけでは「2 回目が成功する」という今回の期待動作までは述べません。
そこを具体的な検査で補います。

既存の `activate_valid` は、妥当な入力状態から起動上限を守ることを示します。
`reachable_valid` は、初期状態から任意の有限操作列を実行した結果の妥当性を示します。
前提と結論は [Task/Proofs.lean](https://github.com/4ge32/lean-cp-os/blob/main/LeanCpOs/Task/Proofs.lean)、
エラー契約は [Task/Semantics.lean](https://github.com/4ge32/lean-cp-os/blob/main/LeanCpOs/Task/Semantics.lean)で読めます。

一般モデルを独立した Python オラクルと比較するには、次を実行します。

```sh
python3 tests/test_task_control.py build/task-tests
```

出力の `status: "passed"` を確認します。
この実行だけでは生成 C の比較は行わず、`scalar` は `null` です。
生成 C、QEMU、証明監査まで含む全検証は[次章](09-evidence.md)で扱います。

## 説明と実装の対応を残す

教材はソースファイルを本文に取り込んでいるため、掲載コードと実行コードを別々に管理しません。
今回のような設定例は、例の目的、初期状態、成功と失敗の期待値を一緒に更新します。
将来モデルの動作自体を変更するときには、次の順に確認先を広げます。

1. 要求表の根拠、前提、対象範囲を見直す。
2. 一般モデル、必要なら `Scalar.lean` と C の境界を変更する。
3. 既存定理の結論が引き続き適切か確認し、必要な証明を更新する。
4. 独立オラクルの期待動作とテストケースを見直し、必要なら QEMU の観測を追加する。
5. 学習例、API 一覧、制限の説明を更新し、Book と全検証を実行する。

今回の設定は 2 タスク、優先度 1 と 3、起動上限の合計 3 なので、
容量制限付きアダプターの設定範囲にも収まります。
ただし、この教材を実行しただけで QEMU のタスク設定が変わるわけではありません。

## 少し変えて確かめる

**演習:** `revised` のタスク 1 の起動上限だけを `3` に変更してください。
どの `#guard` が失敗し、なぜ失敗するかを実行前に予想しましょう。

<details>
<summary>答え</summary>

`third.status == .limit` と `third.state == second.state` が失敗します。
3 回目が受理され、新しい `(1, 0)` が待ち行列に追加されるからです。
`third.discard == false` は引き続き成立します。
この教材の終了操作は `third.state` ではなく `second.state` から始めるので、
その後の検査は変わりません。
3 回目の終了まで調べるなら、終了操作の入力も `third.state` に変え、
最終的にタスク 0 が再開するまでの検査を追加します。
実験後は上限を `2` に戻して、教材全体が成功することを確かめてください。

</details>
