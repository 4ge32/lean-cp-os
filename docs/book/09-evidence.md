# 9. 検証結果を読み解く

この章では、検証レポートから「どのソースを、何で確認したか」を読み取ります。
成功したテストの数だけでなく、証明の前提、未実行の工程、残る課題も確認します。
到達目標は、一つの変更に対して適切な根拠を添えてレビューできることです。

## 一つのレポートを開く

[検証履歴の入口](verification.md)から、対象コミットの実行を選びます。
Book の版と、検証されたコミットは別に確認してください。
古いコミットの失敗も履歴に残ります。
最新の一覧に掲載されていることは、現在の `main` が検証済みという保証にはなりません。

手元で全検証を行う場合は、Lean と QEMU を用意し、リポジトリのルートで実行します。
検証は `build/` と `.lake/build/` を作り直すため、Book のビルドと同時には実行しません。

```sh
python3 scripts/verify.py --out evidence/local
```

通常はコミット済みで変更のない作業ツリーが必要です。
編集中の動作確認には `--allow-dirty` を付けられます。

```sh
python3 scripts/verify.py --out evidence/development --allow-dirty
```

変更のある作業ツリーでは `exact_commit: false` と記録されます。
レポートの SHA と同じ内容を検証した、と扱わないでください。
検証中はソースを編集せず、同じ出力先に別の検証を並行実行しません。

## 最初にソースと実行を特定する

`evidence/local/index.html` をブラウザーで開きます。
機械で読む場合は `report.json` を使います。

| フィールド | 確認すること |
|---|---|
| `sha` / `tree_sha` | 対象コミットと、そのファイルツリー |
| `run_id` / `attempt` | Actions のどの実行・再実行か。ローカル実行は `local-...` |
| `exact_commit` | 開始時の作業ツリーが対象コミットと一致したか |
| `source_unchanged` | 開始時と終了時で Git 追跡ファイルの内容、Git 状態、HEAD が一致したか |
| `source_hashes` | 追跡対象ソースの SHA-256 |
| `overall` | 必須工程全体の成否 |
| `coverage` | 要求・実装境界まで含めた検証範囲。現在は `incomplete` |

`source_unchanged` は開始時と終了時の比較です。
未追跡ファイルの内容はハッシュ比較の対象ではありません。
途中で変更して元に戻す操作を常時監視する仕組みではありません。
ハッシュも、ファイルの同一性を確認するもので、内容の正しさを証明するものではありません。

## 成否を工程ごとに読む

`stages` の各行にはコマンド、成否、終了コード、ログが記録されます。

| 状態 | 意味 | 次の行動 |
|---|---|---|
| `passed` | その工程が正常終了 | 何を確認する工程か読む |
| `failed` | エラー、検査不一致、ツール不足、タイムアウトなど | その工程のログを開く |
| `not_run` | 必要な前段が成功しておらず、実行していない | 依存元の最初の失敗を調べる |

例えば QEMU がない場合、`qemu-task-control` は失敗します。
未実行を成功として数えることはありません。
Lean のビルドが失敗した後の C 生成が `not_run` なら、まず `lean-build.log` を読みます。
同じ操作で大量の後続エラーを直そうとする前に、起点を特定しましょう。

## 証明、比較、実行の役割を分ける

| 根拠 | 主に読むファイル | そこで確認できること |
|---|---|---|
| Lean の定理と公理監査 | `axioms.json`、`axioms.log` | 登録された定理の検査と依存公理 |
| 固定 3 タスクの回帰検査 | `test-results/tests.json` | Lean、生成 C、独立オラクルの具体的入力での一致 |
| 設定可能な基本タスク | `test-results/task-control.json` | 一般モデルの比較、操作列、プロトコル検査 |
| 容量制限付き生成 C | 同 JSON の `scalar` | 固定容量の表現とオラクルの具体的入力での一致 |
| 実タスク切り替え | `qemu/qemu.json`、`qemu/uart.log` | スタック・レジスタ保存、再開、新規実行、成功終了後の非復帰 |
| 実行系の観察 | `runtime.json` | 生成コード中の処理やコンパイラーが報告した関数ごとのスタック使用 |

公理監査は、定理の依存として `propext` だけを許可する方針です。
モデルに書かれた性質の証明は、C コンパイラー、アセンブリー、CPU の正しさを含みません。
また、生成コードの呼び出し箇所数は実行時の最大呼び出し回数ではありません。
スタックの関数ごとの値を足すだけで、全実行経路の上限が得られるとも限りません。

一般モデルの単独テストで `scalar: null` なら、生成 C 比較は未実行です。
任意の有限操作列に関する Lean の定理と、長さを限った全列挙テストも区別してください。
後者の具体的な深さ・件数は、その実行の JSON に記録されます。

## 要求との対応から、残る課題を知る

[要求カタログ](https://github.com/4ge32/lean-cp-os/blob/main/trace/requirements.json)は、
根拠資料、定義、定理、テスト、C の境界の対応を持ちます。
カタログにリンクがあるだけで検証済みにはなりません。
`trace.json` は実際の証明監査とテスト結果を読み込み、各要求の状態を生成します。

例えば第 8 章の設定変更では、`LCPO-013` と `LCPO-020` を探します。
`implementation`、`proof`、`test` をそれぞれ読み、次に `assumptions` を確認します。
生成 C との比較は `LCPO-021`、AArch64 実行は `LCPO-018` が別に扱います。

`structural_status: passed` は、参照先や対応表の構造が正しいことを示します。
`coverage_status: incomplete` は、未実装や未証明の境界が残っていることを示します。
全工程が通った `overall: passed` と両立します。
AUTOSAR 全体への適合、実割り込みの安全性、WCET まで証明したという意味にはなりません。

## 履歴の失敗と現在の失敗を区別する

push 時の CI は、導入された複数のコミットをそれぞれの検証器で検査します。
現在のコミットが成功していても、途中のコミットの失敗で実行全体が失敗する場合があります。
まず `targets.json` と各 SHA のレポートを確認します。
現在の先端だけを確認したい場合は、Actions の **Run workflow** で対象ブランチを選び、
`scope: head` を使います。古い実行の再実行は、その時点のワークフローを使います。

## 確かめる

**演習:** 次の結果から、レビューに何を書けるでしょうか。
`overall: passed`、`exact_commit: false`、`coverage: incomplete` です。

<details>
<summary>答え</summary>

「編集中の作業ツリーで全工程が成功した。コミットそのものの検証結果ではなく、
未証明・未対応の範囲は残る」と書けます。
記録された SHA の成果として公開する前には、変更をコミットし、
変更のない状態で改めて検証する必要があります。
具体的な未確認事項は `trace.json` の `gaps` と各要求の状態から引用します。

</details>
